这份文档有两个用途：一是帮你读懂这个工程（设计是什么、验证平台怎么搭的、每个用例各测什么）；

## 1. 被测设计 MCDF

MCDF（Multi-Channel Data Formatter，多通道数据整形器）把三个输入通道的数据打包后从一个出口送出去。

```
ch0 ──► slave_fifo0 ─┐
ch1 ──► slave_fifo1 ─┼─► arbiter ──► formater ──► fmt_*（数据包）
ch2 ──► slave_fifo2 ─┘      ▲            
                            │ 优先级 / 包长 / 使能
              寄存器总线 ──► ctrl_regs
```

| 模块 | 文件 | 作用 |
|---|---|---|
| `ctrl_regs` | `dut/reg.v` | 6 个寄存器：3 个控制寄存器（可读写）、3 个状态寄存器（只读） |
| `slave_fifo` ×3 | `dut/slave_fifo.v` | 每通道一个 32 深度的 FIFO，`ready = 未满 && 通道使能` |
| `arbiter` | `dut/arbiter.v` | 在有数据的通道里按优先级选一个 |
| `formater` | `dut/formater.v` | 攒够一个包的数据后向下游申请发送（req/grant），再逐字送出 |

**寄存器表**（地址 8 位，数据 32 位）

| 地址 | 寄存器 | 复位值 | 位定义 |
|---|---|---|---|
| 0x00 / 0x04 / 0x08 | 通道 0/1/2 控制寄存器 | 0x07 | bit0 使能；bit[2:1] 优先级（**0 最高**，3 最低）；bit[5:3] 包长码（0→4，1→8，2→16，3→32，4~7→32）；其余保留，写不进去 |
| 0x10 / 0x14 / 0x18 | 通道 0/1/2 状态寄存器 | 0x20 | bit[7:0] FIFO 剩余可写数量，只读 |

**三组接口的时序要点**

- **寄存器总线**（类似 APB）：一次读写占 2 拍。第 1 拍 `psel=1, penable=0`（读操作在这一拍结束时把数据放到 `prdata`），
  第 2 拍 `penable=1`（写操作在这一拍结束时生效）。可以背靠背连续访问。
- **通道接口**：`ch_valid && ch_ready` 同时为高的时钟沿写入一个数据。
- **整形器接口**：攒够数据后拉高 `fmt_req` → 下游给 `fmt_grant` → `fmt_start` 那一拍送出第 0 个数据，
  之后每拍一个，最后一个数据那拍 `fmt_end` 为高。`fmt_chid` 是来源通道，`fmt_length` 是包长。
- **仲裁规则**：有数据的通道里优先级数值最小的赢，数值相同则通道号小的赢。这是静态优先级，高优先级通道一直有数据时低优先级通道会被饿死。

## 2. 验证平台结构

```
case0 ~ case4 （都继承 base_test）
 ├─ v_sqr   虚拟 sequencer，持有下面各 sequencer 和寄存器模型的句柄
 └─ env （env_mcdf）
     ├─ chnl_agts[0..2]  通道 agent：sequencer + driver + monitor
     ├─ reg_agt          寄存器总线 agent：sequencer + driver + monitor
     ├─ fmt_agt          整形器 agent：driver 扮演下游接收方（给 grant、收数据），monitor 采集数据包
     ├─ rm + adapter + predictor   寄存器模型、总线适配器、预测器
     ├─ mdl              参考模型：把通道 monitor 采到的数据按寄存器里的包长切成"期望数据包"
     ├─ scb              scoreboard：比较期望包与整形器 monitor 采到的实际包，外加两个协议检查
     └─ cov              功能覆盖率（只在 +define+COV_EN 时创建）
```

数据流是这样闭环的：

1. 通道 driver 把数据送进 DUT，通道 monitor 在握手成功时把同一个数据交给参考模型。
2. 参考模型读寄存器模型里该通道的包长，每攒够一包就生成一个期望包，放进该通道的队列。
3. 整形器 monitor 在出口采到一个完整的包（通道号、长度、数据）交给 scoreboard。
4. scoreboard 按通道号取出期望包，用 `compare()` 比较，打印 `[CMPSUC]` 或 `[CMPERR]`。

scoreboard 里还有两个独立的检查线程：

- `do_channel_disable_check`：通道关闭时如果还出现 `valid && ready`，报 `[CHKERR]`。
- `do_arbiter_priority_check`：仲裁时刻，优先级最高的请求通道必须在下一拍得到应答，否则报 `[CHKERR]`。

**寄存器模型**在这个平台里涉及三件事：

- 前门访问：case0 / case1 的 `write()` / `read()`、case2 的 `set()` + `update()`，都经 adapter 变成总线事务，由 `reg_agt` 的 driver 发出去。
- 显式预测：总线 monitor 看到的每次访问交给 `uvm_reg_predictor`，更新寄存器模型的镜像值。
- 后门访问：case2 的 `mirror(status, UVM_CHECK, UVM_BACKDOOR)` 直接通过 HDL 路径 `tb_top.dut.ctrl_regs_inst.mem[N]` 读 DUT 里的值，与镜像值比较。

不经过寄存器模型也能访问总线：直接在 `reg_sqr` 上启动 `sequence_bus`，地址和数据可以任意给。
原有用例只用它发 IDLE 命令，case4 用它访问没有寄存器的地址。driver 本身发不出来的总线情况（例如 `psel` 为 0 时 `penable` 为 1），
case4 是在 sequence 里通过接口句柄直接驱动信号做的。

**激励是怎么起来的**：每个用例在 `build_phase` 里用 `uvm_config_db` 把两个虚拟序列设成 `v_sqr` 的 `default_sequence`：
`configure_phase` 跑寄存器配置序列，`main_phase` 跑数据序列。序列自己通过 `starting_phase` 提起（raise）和撤销（drop）objection 来控制阶段何时结束。

## 3. 用例

### 3.1 原有的三个用例

| 用例 | 寄存器配置 | 数据 | 检查点 | 期望比较次数 |
|---|---|---|---|---|
| case0 | 包长 4 / 8 / 16，优先级全 0 | 三个通道**依次**发送：40×8、20×16、10×32 个数据 | 数据比较 | 80 + 40 + 20 = 140 |
| case1 | 包长 8 / 16 / 32，优先级 0 / 1 / 3 | 三个通道**同时**发送，各 100 个事务 | 数据比较 + 每个寄存器写后回读比较 | 100 + 100 + 100 = 300 |
| case2 | 随机包长（4 或 8）和优先级，用 `set()` + `update()` 写入 | 随机事务数（400~600）、随机数据量和间隔 | 数据比较 + 后门 `mirror` 检查 | 随种子变化 |

比较次数可以手算：通道发送的数据总数 ÷ 包长。例如 case0 的通道 0 发 40×8 = 320 个数据，包长 4，所以是 80 个包。

**case0 的关键时刻**（Verilator 日志和独立模型一致，可以对着波形看）：

| 时间 | 事件 |
|---|---|
| 5 ns | 第一个时钟上升沿，DUT 开始处于复位状态 |
| 105 ns | `rstn` 释放；115 ns 是 DUT 复位后的第一个有效沿 |
| 116 ns | 第一次寄存器写出现在总线上；135 ns 写入生效 |
| 145 ns | 日志打印第一条 `monitored addr 00, cmd write`（monitor 比 driver 晚一拍看到） |
| 235 ns | 3 写 3 读完成；再等 500 ns，735 ns 配置阶段结束 |
| 846 ns | 通道 0 的第一个数据出现 |
| 985 ns | 第 1 次比较成功 |
| 22905 ns | 第 140 次比较成功 |
| 27065 ns | 等待 5 µs 排空后仿真结束 |

case1 里因为通道 0 优先级最高且一直有数据，输出顺序是先出完通道 0 的 100 包，再出通道 1，最后通道 2。

### 3.2 后来补的两个用例

第 4 节的覆盖率和第 5 节的变异测试都指出：原来三个用例从不关通道、从不读状态寄存器、也不检查复位值。
`case3` 和 `case4` 就是为这几处补的。文件都在 `testbench/component/case/`：

| 文件 | 内容 |
|---|---|
| `case3.sv` | 通道关闭和优先级用例 |
| `case4.sv` | 寄存器用例 |
| `case_common.sv` | 两个用例共用的部分：整形器输出检查器 `pkt_order_checker`；虚拟序列的基类 `case_common_vseq`（读寄存器并比较、直接发总线读写、按优先级排序）；用例的基类 `case_common_test`（超时、结束检查） |

它们用的都是平台里已有的 agent、sequence、寄存器模型、参考模型和 scoreboard，原有的组件一行没改。

| 用例 | 测什么 | 数据 | 期望比较次数 |
|---|---|---|---|
| case3 | 通道使能 / 关闭；两个和三个通道之间的优先级（包括优先级相同）；下游变慢时的 grant 握手 | 包长 4 / 8 / 16，每个通道一共发 448 个数据 | 112 + 56 + 28 = 196 |
| case4 | 寄存器和寄存器总线；FIFO 里存着数据时的状态寄存器 | 配置阶段不发数据，只检查寄存器；主阶段发少量数据来核对状态寄存器，包长 8 / 16 / 32 | 7 + 4 + 3 = 14 |

两个用例的检查结果都和种子无关：换种子以后，比较结果、总线上的每一次访问和用例自己的检查都不变。
随种子变化的只有两处：一个 IDLE 总线命令里没有用到的随机地址和数据；case3 最后一轮（慢速下游）的时间，因为下游取数的节奏是随机的。

**这两个用例改过三版。** 每写完一版，就请一个独立评审只读代码、专找"检查不会失败"的地方，并把找到的每个漏洞写成一个具体的 bug（变异体）；
先在当前版本上实际跑一遍，确认它真的漏检，再改用例。第一轮评审提出 4 个（m18~m21），第二轮提出 10 个（m22~m31），结果见第 5 节。
下面描述的是第三版。

**整形器输出检查器 `pkt_order_checker`**

它在每个时钟的下降沿看整形器的输出（这时 DUT 的输出都已稳定，和时钟块的采样时序无关），做两件事：

1. 记下每个包来自哪个通道（`fmt_start` 为高那一拍的 `fmt_chid`）。虚拟序列在每一段数据发完、排空之后调用 `check_order()`，
   把这段时间出来的包的通道顺序和期望顺序比较：多一个包、少一个包、顺序不对都报 `[order_check]` 错误。
   期望顺序是用例根据**写进寄存器的**优先级算出来的，不看 DUT 内部的信号。日志里每次检查打印一行，
   例如 `round 0, part 0: the packets came out of MCDF in the expected order ch2 x2, ch1 x4`。
2. 检查整形器接口的协议（原平台里没有任何地方检查它们），出错报 `[fmt_check]`：
   一个包只能在 `fmt_grant` 为高时开始；上一个包没结束之前不能开始新包；`fmt_end` 只在每个包最后一个数据的那一拍为高。

为什么需要第 1 条：scoreboard 按通道比较，从 MCDF 出来一个通道 2 的包，就和参考模型给通道 2 算出的下一个期望包比。
它不管不同通道的包谁先谁后，所以看不出"优先级用错了"。scoreboard 里另有一个仲裁检查 `do_arbiter_priority_check`，
但它判断"谁该赢"用的优先级是从 DUT 仲裁器的输入端口上取的（`tb_top` 把 `arbiter_inst.slvN_prio_i` 接到了 `arb_if` 上）。
如果寄存器到仲裁器的连线本身错了，它拿到的也是错的值，照样认为仲裁正确（第 5 节的 m18 就是这样漏掉的）。

**case3：通道关闭和优先级**

第 0~2 轮，每轮关一个通道（第 0 轮关通道 0，依此类推）。一轮里做四件事：

1. 把这一轮要关的通道的使能位写 0，然后向它发 2×16 个数据。它的 driver 会把 `valid` 拉高然后一直等 `ready`，
   所以这个 sequence 放在 `fork ... join_none` 里。MCDF 不能收这个通道的任何数据：
   scoreboard 的 `do_channel_disable_check` 每一拍都在看"通道关着的时候不能出现 `valid && ready`"，原来三个用例里这个检查从来没有机会起作用。
2. 另外两个通道同时开始发数据，分三段，每段各发 2×16 个：第一段编号大的那个通道优先级更高，第二段反过来，第三段两个一样（这时编号小的赢）。
   每段排空后检查出包顺序。
3. 检查被关的通道：它的 sequence 还没结束（数据没有被收走），它的状态寄存器是 0x20（FIFO 是空的）。
4. 把使能位写回 1，被挡在门外的 32 个数据必须全部进入并送出，然后再检查一次出包顺序。

优先级表（代码里的 `prio_tab`）和期望的出包顺序（日志里的 `[order_check]` 和它一致）：

| 轮次 | 被关的通道 | 段 | 通道 0 / 1 / 2 的优先级 | 出包顺序 |
|---|---|---|---|---|
| 0 | 通道 0 | 1 | 3 / 2 / 0 | ch2 x2, ch1 x4 |
| | | 2 | 3 / 1 / 3 | ch1 x4, ch2 x2 |
| | | 3 | 3 / 2 / 2 | ch1 x4, ch2 x2（优先级相同，编号小的赢） |
| | | 重新打开 | | ch0 x8 |
| 1 | 通道 1 | 1 | 2 / 3 / 1 | ch2 x2, ch0 x8 |
| | | 2 | 0 / 3 / 2 | ch0 x8, ch2 x2 |
| | | 3 | 1 / 3 / 1 | ch0 x8, ch2 x2（相同） |
| | | 重新打开 | | ch1 x4 |
| 2 | 通道 2 | 1 | 1 / 0 / 2 | ch1 x4, ch0 x8 |
| | | 2 | 2 / 3 / 2 | ch0 x8, ch1 x4 |
| | | 3 | 1 / 1 / 3 | ch0 x8, ch1 x4（相同） |
| | | 重新打开 | | ch2 x2 |

期望顺序是这样推出来的：两个通道在同一拍开始发数据，优先级高的那个先拿到整形器；它每发完一包，FIFO 里都已经有下一包的数据，
所以它会连着赢，直到把自己的包都发完，然后才轮到另一个。
这样排，三对通道（1 和 2、0 和 2、0 和 1）在"编号大的赢""编号小的赢""优先级相同"三种情况下都分过胜负，
其中"只有通道 0 和通道 2 有数据"这种情况，原来三个用例里从来没有出现过；每个通道也都用到了 0~3 四个优先级取值。

第 3 轮，三个通道都打开，同时开始各发 2×16 个数据，换 5 组优先级（代码里的 `prio3_tab`）：

| 段 | 通道 0 / 1 / 2 的优先级 | 出包顺序 | 三个通道都有请求时，`arbiter.v` 走的分支 |
|---|---|---|---|
| 0 | 2 / 1 / 1 | ch1 x4, ch2 x2, ch0 x8 | 第 103 行：通道 1 最好，通道 2 比通道 0 好（通道 1、2 相同） |
| 1 | 1 / 1 / 2 | ch0 x8, ch1 x4, ch2 x2 | 第 95 行：通道 0 最好（通道 0、1 相同） |
| 2 | 1 / 2 / 1 | ch0 x8, ch2 x2, ch1 x4 | 第 95 行（通道 0、2 相同） |
| 3 | 1 / 0 / 2 | ch1 x4, ch0 x8, ch2 x2 | 第 99 行：通道 1 最好，通道 2 不比通道 0 好 |
| 4 | 2 / 2 / 0 | ch2 x2, ch0 x8, ch1 x4 | 第 107 行：通道 2 最好 |

期望顺序就是按（优先级，通道号）从小到大排：最好的通道先发完它所有的包，然后第二个，最后第三个。
第 99、103 行这两个分支，原来的用例一次也没有走到过（第 4 节）。

第 4 轮，把整形器 agent 改成"小缓冲、慢消费"（`SHORT_FIFO`、`LOW_WIDTH`），三个通道再各发 4×16 个数据。
下游的缓冲很快就满了，driver 常常要等一会儿才给 `fmt_grant`。出包顺序不能变，而且每个包都必须在拿到 grant 以后才开始（`pkt_order_checker` 的第 2 条）。
前两版里所有的下游都是"立即给 grant"，"整形器不等 grant 就发包"这种 bug 根本暴露不出来（第 5 节的 m28）。
这一轮的时间随种子变化，检查的结果不变。整个用例约 63 µs。

**case4：寄存器**

配置阶段（`case4_cfg_vseq`）不发数据，按顺序做 7 步，每一步结束都把相关寄存器读出来比较：

| 步骤 | 做法 | 期望 |
|---|---|---|
| 1 复位后 | 复位期间故意把总线上的 `pwrite` 置为 1（`psel` 为 0，协议允许）；复位后什么都不写，先读 6 个寄存器 | 控制寄存器 0x07（复位值）；状态寄存器 0x20（FIFO 空） |
| 2 写后回读 | 每个控制寄存器的 64 种取值全部写一遍再读回。同一时刻三个寄存器的值互不相同；偶数轮按 0、1、2 的顺序写，奇数轮按 2、1、0 | 读回值等于写入值。丢位、翻转位、写到或读到别的寄存器都会被发现；"写一个寄存器时把另一个也改了"在两种顺序之一里会被发现 |
| 3 保留位 | 写入高 26 位带 1 的数据（如 0xFFFF_FFFF），同样换两种顺序 | 读回只剩低 6 位 |
| 4 只读 | 往每个状态寄存器写 0xFFFF_FFFF 和 0，每次写完紧接着读同一个寄存器 | 读回仍是 0x20；最后 6 个寄存器都不变 |
| 5 非法地址 | 0x00~0xFF 里没有寄存器的 250 个地址，逐个写 0xFFFF_FFFF 再读一次 | 6 个寄存器都不变（读回的数据没有定义，不检查） |
| 6 读不改寄存器 | 读 6 个寄存器，读的同时在写数据线上放 0xFFFF_FFFF | 读回值正确，之后 6 个寄存器都不变 |
| 7 别的从设备的传输 | 先读控制寄存器 k，再在总线上做一次"发给别的从设备的写"：`psel` 保持 0，`penable` 和 `pwrite` 照常变高，数据全 1 | 6 个寄存器都不变 |

几个细节：

- 状态寄存器每拍都从 FIFO 重新装载，所以它自己的复位值在总线上看不到，第 1 步读到的 0x20 说明的是"FIFO 空"。
- 同样因为每拍重新装载，假如状态寄存器被错误地写进了一个值，下一拍就又被覆盖了。只有紧接着的那次读才看得到它：
  总线读在访问的第 1 拍取数，正好是写生效后的下一拍。第一版是写完三个状态寄存器以后再统一读，这种 bug 就漏过去了（第 5 节的 m19）。
- 第 1 步和第 7 步考的是"总线上的其它情况"。APB 是共享总线，`psel` 为 0 时其它信号是什么都可以；
  一个从设备如果写使能里漏了 `psel`（m22），或者状态机复位到了错误的状态（m26），只有在 `psel` 为 0 而 `pwrite` / `penable` 为 1 时才会出错。
  原平台的总线 driver 永远不会产生这种情况，所以这两步是在 sequence 里、趁 driver 空闲时直接驱动总线信号做的。
- 第 7 步之前先读一次控制寄存器 k，是为了让 MCDF 最后看到的地址正好是 k：漏了 `psel` 的写使能会把数据写进这个地址。

第 1~3 步用寄存器模型的 `write()` / `read()`；第 4~6 步的访问寄存器模型发不出来（没有对应的寄存器，或者读的时候要控制写数据线），
所以直接用 `sequence_bus` 发总线事务；第 1、7 步的情况连 driver 也发不出来，只能直接驱动接口信号。

主阶段（`case4_vseq`）是第 8 步：**FIFO 里存着数据时，状态寄存器要等于"32 − 数据个数"**。
难点在于数据正常流动时 FIFO 里的个数每拍都在变，没法精确比较。这里利用了 DUT 的一个特性：
一个通道被选中以后，整形器要凑够一整包才会去服务别的通道（第 6 节 DUT 部分第 2 条）。

主阶段的配置：通道 0 / 1 / 2 的包长是 8 / 16 / 32，优先级是 2 / 1 / 0。每一轮这样做（以第 1 轮为例）：

1. 先给通道 2（"占位"的通道）发 4 个数据。这 4 个数据马上被整形器取走，然后整形器停下来等这一包剩下的 28 个，不再服务别的通道。
2. 给通道 0 发 9 个数据；同时总线上不停地背靠背读（`psel` 一直为高），在同一串访问里紧接着读通道 0 的状态寄存器：应该是 0x17（32−9）。
3. 给通道 1 发 22 个数据，读三个状态寄存器：0x17、0x0A（32−22）、0x20。
4. 把通道 0 补到 16 个、通道 1 补到 32 个（都是整包），再读：0x10、0x00（FIFO 满）、0x20。
5. 关掉通道 0 和通道 1：数据还在 FIFO 里，状态寄存器的值不变，再读一次。
6. 把通道 2 剩下的 28 个数据补上。整形器凑够一包，所有数据依次送出（关掉的通道不再收新数据，但 FIFO 里已有的数据照样送出），
   scoreboard 照常比较；再读，三个状态寄存器都回到 0x20。然后把通道 0、1 重新打开。
7. 出包顺序必须是：通道 2 的 1 包，然后有数据的通道按优先级各自把包全部发完：先通道 1（优先级 1），再通道 0（优先级 2）。

三轮的安排（日志里的读数和这张表一致）：

| 轮次 | 占位通道 | 等待的数据（个数） | 第 3 步：状态 0 / 1 / 2 | 第 4、5 步 | 出包顺序 |
|---|---|---|---|---|---|
| 1 | 通道 2 | 通道 0：9 → 16；通道 1：22 → 32 | 0x17 / 0x0A / 0x20 | 0x10 / 0x00 / 0x20 | ch2 x1, ch1 x2, ch0 x2 |
| 2 | 通道 0 | 通道 1：11 → 16；通道 2：22 → 32 | 0x20 / 0x15 / 0x0A | 0x20 / 0x10 / 0x00 | ch0 x1, ch2 x1, ch1 x1, ch0 x1 |
| 3 | 通道 1 | 通道 2：11 → 32；通道 0：24 | 0x08 / 0x20 / 0x15 | 0x08 / 0x20 / 0x00 | ch1 x1, ch2 x1, ch0 x3 |

第 2 步（总线忙时）读到的，就是表中第一个等待通道在第 3 步的值：0x17、0x15、0x15。

第 2 轮有一点特别：占位的通道 0 补数据时多发了一整包。它发完第一包时手上还有数据，但优先级最差（2），
必须先让通道 2（优先级 0）和通道 1（优先级 1）发，最后才轮到自己。"当前通道还有数据就一直占着整形器"这种仲裁 bug（第 5 节的 m31）会在这里暴露。

数字是特意选的：

- 状态寄存器 0 读到过 0x17 和 0x08，另外两个读到过 0x15 和 0x0A。这两对的低 5 位互补；第 5 位只在 0x20（FIFO 空）时为 1，
  而每个状态寄存器也都读到过 0x20。所以**每个状态寄存器的第 0~5 位都在 1 和 0 上各检查过一次**；第 6~31 位永远是 0，只能检查它是 0。
  第一版只读到过 4 的倍数，最低两位从来没被检查过（第 5 节的 m21）。
- 表里每一次读，三个寄存器的值都互不相同，所以"状态寄存器显示的是别的通道"一定会被发现。
- 第 2 步在总线一直忙的时候读，是为了发现"状态寄存器只在总线空闲时才更新"这种 bug（m25）；
  第 5、6 步在通道关着的时候读，是为了发现"通道关闭时状态寄存器不更新"这种 bug（m23）。

读状态寄存器还有一个时序细节：状态寄存器比 FIFO 晚一拍更新，所以发完数据要等几拍再读（代码里是 `#100`；总线忙时是多读两次再读状态寄存器）。

**两个用例共有的部分**（`case_common_test`）

- **整形器输出检查器**：见上面。
- **自带超时**：`run_phase` 里起一个进程，1 ms 仿真时间以后报 `UVM_FATAL [TIMEOUT]`。用例正常不到 70 µs 就结束；如果某个通道一直不收数据，
  driver 会永远等 `ready`。没有这个超时，只能等 Makefile 的墙钟上限（默认 1800 秒）把仿真杀掉；
  在没有墙钟上限的流程里（原 VCS 流程），要一直跑到 `+UVM_TIMEOUT`（1 s 仿真时间，在 Verilator 上要几个小时）。
  延时写在用例自己的代码里，按用例的时间单位计算，和 UVM 库编译时用的时间单位无关。
- **结束检查**（`check_phase`）有两条。一是最后一次顺序检查之后没有再出来包：结尾多出来一个包时，scoreboard 只会卡住，
  等一个永远不来的期望包，自己不报错。二是参考模型里没有剩下的期望包：少出来的包、scoreboard 卡住以后没再比较的包都会在这里暴露
  （第 5 节的 m10 在 case0 / case1 里就是这样漏过去的）。这两条只对 case3 / case4 生效。

**写第三版时踩到的一个坑**：原平台的总线 driver 要求每次访问都在时钟上升沿所在的时间步开始（第 6 节测试平台第 12 条）。
第三版一开始在下降沿等包出来，排空后紧接着的寄存器写就是在下降沿开始的。这次写丢了 SETUP 那一拍，
DUT 把下一次访问的数据写进了这个地址，case3 第 3 轮因此报了一串 CMPERR。现在 `wait_packets()` 最后会再等到一个上升沿。

这两个用例只在 Verilator 上跑过。`sim/runlist` 里也加了它们，但没有在 VCS 上验证；可能的差别见第 6 节测试平台部分。

这 31 个变异体是分四批来的，读结果时要分开看：

- **m01~m12** 是移植完成后做评估时定的，那时还没有 case3 / case4，其中 m07、m11、m12 三个漏检。这三个现在分别被 case3、case4、case4 抓到，
  这是补用例的直接目的。
- **m13~m17** 是写第一版 case3 / case4 时加的，本来就是对着新增的检查点注入的，所以它们被检出并不意外。
  它们的作用是证明这些检查"真的会报错"，而不只是"跑到了"；同时也说明原来三个用例在这些地方确实是盲区。
- **m18~m21** 来自对第一版的独立评审。把这 4 个 bug 拿到第一版用例上实际跑了一遍：**m18、m19、m21 在全部五个用例下都通过，确实漏检**；
  m20 倒是被第一版 case3 碰巧抓到了——通道 1 关着、`valid` 一直为高时写了控制寄存器 0，bug 顺带把通道 1 的使能打开了两拍，
  漏进去几个数据，后面的包错位，于是数据比较失败。这不是哪项检查有意抓到的，换一种写寄存器的顺序就抓不到了。
  第二版针对这几处加了出包顺序检查、状态寄存器写完紧接着读、两种写入顺序、奇数个等待数据。
- **m22~m31** 来自对第二版的第二轮独立评审。同样先在第二版上实际跑：**10 个全部漏检**。第三版据此加了：
  `psel` 为 0 时的总线传输和复位期间的 `pwrite`（m22、m26），通道关闭和总线忙时的状态寄存器（m23、m25），
  优先级相同和三个通道同时请求的仲裁（m27、m30），当前通道还有数据时的重新仲裁（m31），慢速下游和整形器协议检查（m28、m29）。
  其中 m24 没有补：要在包长码为 4~7 时发数据，得先改原平台参考模型里的包长公式（第 6 节测试平台第 3 条、第 8 节第 1 条），这超出了"补用例"的范围。

所以不要把 30/31 理解成"测试平台已经没有漏洞"。第一版的 17/17、第二版的 21/21 也都是"全部检出"，评审照样又各找出了一批漏检的 bug。
这正是变异测试的局限：它只能告诉你"这些 bug 抓得到"，至于有哪些 bug 没想到，要靠评审、覆盖率和规格一条一条地对。

几点观察：

- **原来漏检的 3 个里有 2 个正好对应第 4 节的覆盖率缺口**：没有关通道的用例（m07）、没有读状态寄存器（m12）；m11 则是因为没有任何用例检查复位值。
  覆盖率缺口和变异测试漏检指向同一个地方时，那里就是最该补用例的地方。反过来，第二轮评审找到的 bug 大多在**已经被覆盖**的代码上（第 4 节）。
- **m10 暴露了一个更隐蔽的问题**：case0 和 case1 在 DUT 明显出错时仍然打印 `TestCase Passed`。
  原因是通道号错了以后 scoreboard 去等一个永远不会来的期望包，线程卡住，后面的包不再比较；
  而原平台通过与否只看 `UVM_ERROR` 的个数，不看比较了多少包。所以**看回归结果时要同时看比较次数**
  （case0 应为 140，case1 应为 300，case3 应为 196，case4 应为 14）。`sim_verilator` 的 Makefile 会在每个用例后面打印比较了多少包，并且把一个包都没比较的运行判为失败；
  `./run.sh check` 则会核对 case0 / case1 的 140 / 300 这样的确切数字。
  case3 / case4 抓 m10 有三道关：三个通道的包长各不相同，通道号一错长度就对不上（CMPERR）；出包顺序检查看到的通道号不对（order_check）；
  结束检查发现参考模型里还剩着期望包（end_check）。
- m04 和 m06 在 case2 里是被后门 `mirror(UVM_CHECK)` 抓到的，说明寄存器后门访问在 Verilator 下确实读到了 DUT 内部的值。
- **m16 是靠超时抓到的**：通道 1 被错误地跟着通道 0 一起关掉，它的 driver 永远等不到 `ready`，case3 / case4 在 1 ms 时以 `UVM_FATAL [TIMEOUT]` 结束。
  没有这个超时，仿真会一直空转到 Makefile 的墙钟上限。
- **每个用例各有侧重，不是越新越强**：m02（某一个特定数据被写错）只有原来三个用例能抓到，case3 / case4 的数据里没有那个值。
  m09（FIFO 溢出）在 case3 里是第 4 轮抓到的：那一轮每个通道发 64 个数据，比 FIFO 深度多，不报满就会把数据挤丢。
- m05 在 case4 里除了 reg_check 还引出了 CMPERR：读回的值是错的，预测器就把寄存器模型里通道 1 的包长更新成了错的值，
  参考模型按错的包长切包，于是数据比较也失败。寄存器模型一旦被带偏，后面的检查都会受影响。
- **m18 只有出包顺序检查能抓到**：通道 1 的优先级被接成了通道 0 的，但 scoreboard 的仲裁检查用的也是这根错的线，所以它认为仲裁完全正确；
  数据比较按通道进行，每个包的内容也都对。只有"按写进寄存器的优先级，这一段应该先出通道 1 的包"这个推算会落空：
  case3 第 2 轮第 1 段报 `the packets came out of MCDF in the order ch0 x8, ch1 x4, expected ch1 x4, ch0 x8`。
- **m28 只有在下游真的让整形器等的时候才会暴露**：快速下游总是在整形器进入等待状态的同一拍给出 grant，"等"和"不等"的波形完全一样。
  所以第三版的 case3 专门加了慢速下游的第 4 轮；同一个检查在前三轮里永远不会失败。
- **m27、m30、m31 改的都是已经被覆盖的代码行**，问题在于没有用例构造出那个条件：优先级相同、三个通道同时请求、当前通道还有数据时有更好的通道在等。
  case3 第 0~2 轮的第 3 段、第 3 轮，case4 第 8 步第 2 轮就是分别为它们加的。

## 6. 发现的问题（都是原工程自身的问题，不是移植引入的）

**测试平台**

1. 没有测试结束时的完整性检查：期望队列里剩下的包、卡住的 scoreboard、结尾多出来的包都不会报错（见上面的 m10）。
   case3 / case4 通过共同的基类 `case_common_test` 补了这个检查（第 3.2 节），原来三个用例仍然没有。
2. 通道关闭检查 `do_channel_disable_check` 在原来三个用例里从未被触发过，因为使能位恒为 1（case2 用的是 `$urandom_range(1,1)`）。case3 补上了。
3. 参考模型的包长公式是 `4 << 包长码`，包长码 ≥ 4 时会算出 64~512，而 DUT 和规格都是 32。现有用例发数据时不会用这么大的包长码，所以没暴露
   （case4 第 2 步会把 4~7 写进寄存器再读回，但那时不发数据）。
4. `cg_mcdf_reg_illegal_access` 里 `cmd` 的两个 bin 名字写反了（`write = {1'b0}`）。对覆盖率的影响见第 4 节末尾。
5. case1 的注释写"prio=2"，代码实际写的是 3。
6. 通过判定不统计 `$error`：序列里的 `assert(rsp.rsp) else $error(...)` 即使触发，UVM 也不计数，按 IEEE 语义仿真会继续跑并照样打印通过
   （Verilator 下 `$error` 会直接终止仿真，反而更显眼）。
7. case2 里连续 `set(); update();` 会重复写寄存器：预测器比 driver 晚一拍更新镜像值，下一次 `update()` 时上一个寄存器看起来还"需要更新"，于是又被写了一次。
   三个随机值都不等于复位值 0x07 时，总线上是 00、00、04、04、08 共 5 次写而不是 3 次；随机值恰好等于 0x07 的寄存器不需要更新、完全不会被写，
   所以实际的写次数在 0～5 之间（40 个种子里：5 次 25 个，4 次 5 个，3 次 9 个，2 次 1 个）。值相同，无害。
   这是在 Verilator + UVM 1800.2-2020.3.2 上观察到的；VCS 自带的 UVM 1.1 遍历寄存器的顺序可能不同，重复的次数未必一样（未实测）。
8. 测试平台依赖一个 IEEE 1800 标准里明确属于竞争的行为：`@(posedge clk)` 之后立刻读时钟块输入（`vif.mon_ck.xxx`），
   读到的是上一拍的采样值还是这一拍的，标准不规定。整形器 monitor 只有在读到"上一拍"时才能正确对齐数据包。
   Verilator 5.054 的行为是确定的"上一拍"，所以能工作（原工程能在 VCS 上跑通，可以推断 VCS 也是这样，但没有实测）。
   如果自己写新的 monitor，用 `@(vif.mon_ck)` 等待时钟块事件可以避开这个竞争，但那样读到的是当前沿的采样，比现有 monitor 早一拍：
   不要把它和现有 monitor 混接到同一个检查器上，也不要只把现有 monitor 改掉一部分。
   （case3 / case4 新加的 `pkt_order_checker` 用的是第三种办法：在时钟下降沿直接读 DUT 输出，那时信号都已稳定，不牵涉这个竞争。）
9. scoreboard 的仲裁检查 `do_arbiter_priority_check` 判断"谁该赢"时，用的是 DUT 仲裁器输入端口上的优先级，而不是写进寄存器的值。
   寄存器到仲裁器的连线错了，它看到的也是错的值，照样认为仲裁正确（第 5 节的 m18）。scoreboard 的数据比较又是按通道进行的，不看不同通道之间的先后，
   所以原平台对"优先级没生效"整体是看不见的。case3 改从写进寄存器的优先级推算出包顺序来检查（第 3.2 节）。
10. `do_channel_disable_check` 在一个原始时钟沿之后，同时读两个不同时钟块（`mcdf_if.mon_ck` 的使能、`chnlN_if.mon_ck` 的 `valid` / `ready`）的采样值。
    按第 8 条，读到哪一拍的值标准不规定；如果某个仿真器对这两个时钟块给出的不是同一拍（一个旧、一个新），
    在 case3 重新打开通道的那一拍（使能从 0 变 1，`valid` 一直是 1），它可能看到"使能还是 0、`ready` 已经是 1"而误报一次 `[CHKERR]`。
    Verilator 下两个都是上一拍的值，不会误报；VCS 下没有验证过。原来三个用例从不改变使能位，所以以前碰不到这种情况。
11. 以 `UVM_FATAL` 结束的运行（例如 case3 / case4 的 1 ms 超时）不会执行 `base_test::report_phase`，所以既不打印 "TestCase Failed"，
    也不往 `sim_result.log` 里写记录。原 VCS 流程的 Makefile 不检查日志，这种失败在那里不留痕迹；`sim_verilator` 的 Makefile 因为找不到 "TestCase Passed" 而判为失败。
12. 寄存器总线的 driver（`driver_bus`）默认每次访问都在时钟上升沿所在的时间步拿到事务。`drive_one_pkt()` 一开始就通过时钟块驱动
    `psel`=1、`penable`=0，接着 `@(posedge clk)` 以后再驱动 `penable`=1。如果事务是在别的时刻（例如时钟下降沿）交给它的，
    第一批驱动要等到下一个上升沿才生效，而紧接着的 `@(posedge clk)` 也在同一个上升沿醒来，于是 `psel` 和 `penable` 同时变高，SETUP 拍没有了。
    DUT 的状态机照样从 IDLE 进 SETUP、再进 ENABLE，但到 ENABLE 那一拍总线上已经是下一次访问的地址和数据，结果**把下一次访问的数据写进了这一次的地址**；
    总线 monitor 也看不到这次访问（它只认 `psel=1, penable=0` 的那一拍）。原来的用例里访问要么背靠背、要么紧跟在复位或整数个时钟周期的延时之后，碰不到这个问题；
    写第三版 case3 时就踩到了（第 3.2 节末尾）。自己写 sequence 时，开始寄存器访问之前要先对齐到时钟上升沿；更彻底的办法是让 driver 自己在开始时先等一个上升沿。

**DUT**

1. 静态优先级，没有轮询，低优先级通道会被饿死（RTL 注释里自己也写了待改进）。
2. 一个通道被选中后必须凑够一整包才会释放整形器；如果发送的数据量不是包长的整数倍，后面的通道会被永远堵住。
   （case4 反过来利用了这一点：故意先发半包，让别的通道的数据停在 FIFO 里，好核对状态寄存器。）
3. `reg.v`、`formater.v` 在 `always @(*)` 里用了非阻塞赋值，`case` 没有 `default`（会推断出锁存器）；
   `arbiter.v` 在时序逻辑里混用阻塞和非阻塞赋值。功能上没出错，但属于不推荐的写法，综合前应该清理。
4. 读一个没有寄存器的地址时，`prdata` 是上一次读操作留下的值，而不是 0（读数据的 `case` 没有 `default`）。
   case4 里 250 个非法地址读回的全是 0x20，就是之前最后一次合法读（通道 2 状态寄存器）的值。规格没有规定这种情况，所以 case4 不检查它。

## 7. 移植过程中确认的几个仿真语义

这些是把一个 VCS 工程搬到另一个仿真器时真正要小心的地方，也是面试里常被问到的点。

- **时钟块驱动**：`@(posedge vif.clk); vif.drv_ck.sig <= v;` 在时钟沿所在的时间步里执行，信号在"这个沿 + 输出偏斜（output skew，1 ns）"变化，
  DUT 在下一个沿采到。所以波形上驱动信号总是在时钟沿之后 1 ns 跳变。
- **时钟块采样**：`mon_ck` 的输入在时钟沿之前 1 ns 采样。但进程如果是被原始时钟沿 `@(posedge vif.clk)` 唤醒的，
  它读到的是上一个沿的采样（见第 6 节第 8 条）。结果就是所有 monitor 的日志都比 driver 晚一拍，例如第一次寄存器写在 135 ns 完成，
  monitor 在 145 ns 才打印。
- **两态与四态**：Verilator 没有 X。`rstn` 在 VCS 里 0~10 ns 是 X，10 ns 变 0 算一次下降沿；在 Verilator 里一开始就是 0，
  没有这个沿。DUT 的异步复位在第一个时钟沿照样生效，所以功能不受影响，只是测试平台里等 `@(negedge rstn)` 的线程不会执行。
- **一个可执行文件跑所有用例**：用例通过 `+UVM_TESTNAME` 在运行时选择，换用例不需要重新编译。

## 8. 可以接着做的事

已经做了的（第 3.2 节）：**通道关闭和优先级用例**（case3：两个和三个通道之间的出包顺序，包括优先级相同的情况，以及慢速下游）、
**寄存器专项用例**（case4），以及它们共用的整形器输出检查器（出包顺序、grant 握手、`fmt_end`）和结束检查（`case_common.sv`）。

还可以接着做的，按投入产出比排序：

1. **修正参考模型的包长公式**，然后加一个发数据时包长码为 4~7 的用例。这是目前唯一已知、却没有用例能覆盖的缺口：
   参考模型按 `4 << 包长码` 算出 64~512，DUT 和规格都是 32（第 6 节测试平台第 3 条），所以任何用例都不能在包长码 ≥ 4 时发数据，
   变异体 m24 因此漏检。改动是 `model.sv` 里的一行公式，属于修改原平台。
2. **把 case3 / case4 的检查放进原平台**：结束检查、出包顺序检查和整形器协议检查现在放在 case3 / case4 自己的基类里，原来三个用例用不到。
   把结束检查（参考模型里没有剩下的期望包、最后不再多出包）移到 scoreboard 的 `check_phase`，m10 在 case0 / case1 里也会被抓到；
   把 scoreboard 仲裁检查用的优先级从 DUT 内部信号改成寄存器模型里的值，m18 这类"优先级没接对"的 bug 就不必靠出包顺序来发现（第 6 节测试平台第 9 条）。
3. **修正总线 driver 的时序假设**：让 `driver_bus` 在开始一次访问前自己先等一个时钟上升沿（第 6 节测试平台第 12 条），
   sequence 就不必关心在什么时刻发起访问。
4. **传输中途关通道**：case3 只在通道空闲时关它，case4 只在数据整包停在 FIFO 里时关它。一包发到一半时关掉会怎样，目前没有用例。
   （注意第 6 节 DUT 第 2 条：半包状态下关通道会把整形器卡住，用例要自己负责把这一包补完。）
5. **给 `cg_arbiter_priority` 加上 cross**：现在它只统计每个通道单独用过哪些优先级，case3 第 3 轮构造的那些组合在覆盖率上看不出来。
6. **换一种写法做寄存器测试**：UVM 自带 `uvm_reg_hw_reset_seq`（复位值）和 `uvm_reg_bit_bash_seq`（逐位读写），
   可以和 case4 里手写的第 1~3 步对照着学；这两个内置序列没有在 Verilator 上试过。
